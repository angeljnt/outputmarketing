# Output Marketing Website Rework Plan

This plan maps the current live website to the new source-of-truth content in:

- `/Users/angeljnt/Agencia Marketing/output_marketing_product_services_marketing_system.md`
- `/Users/angeljnt/Agencia Marketing/output_marketing_website_style_master_page.md`

It is written to preserve the current visual system documented in:

- `/Users/angeljnt/outputmarketing-live/docs/current-design-system.md`

The goal is not to redesign the site from scratch.
The goal is to rework structure, messaging, page hierarchy, and copy so the website reflects the real offer and ICP without breaking the current design language.

## 1. Executive Summary

### What changed strategically

The new source-of-truth docs shift the website from a narrower "founder LinkedIn + content + SEO" story into a broader but still focused B2B SaaS execution offer:

- B2B SaaS marketing for lean teams
- content tied to pipeline
- founder and brand visibility
- SEO with commercial intent
- product and launch marketing
- reporting and accountability
- selective white-label support

### What the current website still does

The live site is visually strong, but its structure and copy still reflect an older narrative:

- hero centers founder LinkedIn + content + SEO only
- service architecture only exposes 3 pages
- launch marketing and reporting are not first-class public offers
- some copy still leans on influencer history too heavily
- some proof and problem framing still mixes in DTC/influencer language
- the site does not yet express the full package-to-service logic from the source docs

### Core rework principle

Keep the current visual system.
Change the content system, page structure, and page order.

This should feel like the same website after a strategic rewrite, not like a brand new aesthetic direction.

## 2. Source-of-Truth Rules

These rules should govern every rewrite:

1. The public story is B2B SaaS-first.
2. The site should speak to lean teams, not enterprise departments.
3. The primary promise is turning content, visibility, and launches into pipeline.
4. `30-Day Pilot` is the default entry point.
5. `Foundation`, `Engine`, and `Full Stack` are the main package ladder.
6. White-label is real, but secondary.
7. Influencer history, DTC work, EdTech, and adjacent experience can support proof, but must not lead the narrative.
8. The site should feel narrower and sharper, not broader and more generalist.

## 3. Current-State Gap Analysis

Current homepage headline and subhead still frame the business mainly as:

Required public service logic from source docs:

- Content Marketing
- SEO Content
- Social and LinkedIn Execution

The current IA creates an offer mismatch before the user even gets to pricing.

Pricing shows `Foundation`, `Engine`, and `Full Stack`, but it does not clearly explain:

- which service families sit inside each package
- how launch/reporting fit the model

Current proof is mostly Archive-led and not consistently translated into capability language.

The source docs want proof mapped by:

- founder and LinkedIn content
- product launches

- technical content and SEO
- reporting and execution systems

The site needs to present proof as capability evidence, not just client history.

### 6. Contact page does not help route intent

The page is clean, but it does not help qualify by:

- package stage
- service family
- SaaS vs white-label fit
- whether the lead needs a pilot, project, or custom scope

### 7. Navigation is structurally thin

The current nav is clean, but it assumes the old 3-service structure.

It needs to support a better services IA without becoming bloated.

## P3 Gaps

### 8. Metadata and SEO copy need alignment

Page titles and descriptions still reflect the narrower offer.

### 9. Terminology is not fully normalized

The current site alternates between:

- content marketing

## 5A. Required Content System Across the Site

The rework should not stop at "better page structure."
It also needs a clear content system so the site consistently explains:

- industries we serve
- services we provide
- packages
- what to expect from each service or package
- what the before/after looks like
- who each offer is for

These modules should be treated as reusable content patterns, not one-off copy fragments.

### 1. Industries We Serve

This content must exist publicly.

It should not just be implied through scattered SaaS references.
Visitors should be able to quickly see whether they are in the right industry cluster.

Recommended industry buckets:

- B2B SaaS and AI SaaS
- Revenue / Sales / Customer Software
- Workflow / Ops / Automation Software
- Analytics / Data / Infrastructure Software
- Secondary fit: Boutique agencies / white-label partners

Recommended content structure for each industry block:

- industry name
- why it fits the offer
- typical pains we help solve
- best package starting point
- strongest related proof angle

Recommended placement:

- homepage: short "Who we are best for" section
- services overview: expanded industry-fit section
- about page: short best-fit confirmation block
- optional later page: `/industries` or `/who-we-serve` if SEO depth becomes valuable

### 2. Services We Provide

The site needs a clearer public service inventory.

Each service family should be described in a consistent pattern.

Recommended public service families:

- Content Marketing
- SEO Content
- Social and LinkedIn Execution
- Product and Launch Marketing
- Measurement and Reporting

For each service, the site should explain:

- what it is
- what is included
- what business problem it solves
- what kind of team it is best for
- which package it usually belongs to
- what proof supports it

Recommended placement:

- homepage: concise service-family summary
- services overview: full public service stack
- each service page: full detail
- pricing: package-to-service mapping

### 3. Packages

Packages should be more than price cards.

Each package should be explained as a stage-based operating model.

Required package content:

- who it is for
- what it focuses on
- what is included at a practical level
- what can be expected during the engagement
- what it is not for
- what the next likely upgrade path is

Recommended package ladder:

- 30-Day Pilot
- Foundation
- Engine
- Full Stack
- secondary custom scopes: White-Label / Capacity Track and Project Track

Recommended placement:

- homepage: concise package summary
- pricing: full package detail
- services overview: package mapping
- contact page: qualification and routing support

### 4. What To Expect From Each Service or Package

This is currently underdeveloped on the live site.

The site should explicitly answer:

- what happens first
- what gets delivered
- what cadence the client should expect
- what kind of communication is involved
- what "good progress" looks like
- what the engagement does not include

This is important because it reduces ambiguity without making the site feel process-heavy.

Recommended expectation pattern:

- first 30 days
- ongoing cadence
- outputs
- reporting rhythm
- ownership and approvals

Recommended placement:

- pricing page: package expectation blocks
- service pages: service-specific expectations
- contact page: short "what happens next" note

### 5. Before / After Transformation Content

The site should include clear before/after framing, but in a sober, credibility-first way.

This should not look like gimmicky makeover copy.
It should look like operational transformation.

Recommended before/after themes:

- before: inconsistent visibility
- after: repeatable visibility

- before: content calendar without business impact
- after: content tied to pipeline

- before: launches announced once and forgotten
- after: launches supported with rollout follow-through

- before: scattered reporting and unclear ROI
- after: clearer measurement and accountability

- before: founder voice missing or inconsistent
- after: founder + brand presence working together

Recommended placement:

- homepage: one high-level before/after section
- service pages: service-specific before/after blocks
- pricing page: stage-based "what changes when this package fits"
- work page: proof-backed before/after framing

### 6. Qualification Checklists

Yes, the site should absolutely include this kind of content.

The cleanest version is not "application form language."
It is:

- `This works for you if...`
- `You are a good fit if...`
- `This is probably not for you if...`

These checklists help visitors self-qualify fast and make the agency feel sharper.

Recommended qualification content types:

#### Service-level qualification

For each service page:

- this service works for you if X, Y, Z
- this service is not the right starting point if X, Y, Z

#### Package-level qualification

For each package:

- team stage
- operational condition
- urgency signal
- likely pain pattern
- what would make a higher or lower tier a better fit

#### Agency-level qualification

On homepage/about/contact:

- best-fit company types
- best-fit team structure
- best-fit growth stage
- low-priority or excluded cases

Recommended placement:

- homepage: short best-fit section
- service pages: explicit fit checklist
- pricing page: package qualification matrix
- contact page: routing question or self-selection prompt
